Vom Formular zum Server — action, method und der Request dahinter

1 · Einstiegsfrage

Du füllst ein Anmeldeformular aus und klickst „Absenden". Die Seite lädt neu — und deine Eingaben sind plötzlich Teil einer Anfrage. Was genau hat der Browser in diesem Moment getan?

  • Wohin gehen die Daten — und in welcher Form?
  • Warum steht bei einer Suche der Begriff in der URL, bei einem Passwort aber nicht?
  • Und was passiert beim Drücken von F5 nach dem Absenden?

Nach dieser UE liest du in den DevTools genau ab, was ein Formular abschickt — und du weißt, was der Server davon zu sehen bekommt.

2 · Ziel-Artefakt: der Netzwerk-Tab, den wir lesen können

Am Ende steht kein hübsches Formular, sondern Verständnis: Du öffnest die DevTools (F12) → Netzwerk, sendest ab und liest den Request.

Anfrage (Browser → Server)
POST /anmeldung HTTP/1.1
Content-Type: application/x-www-form-urlencoded
Content-Length: 68

name=Ada+Lovelace&email=ada%40example.org&kurs=typescript&agb=on

Antwort (Server → Browser)
HTTP/1.1 303 See Other
Location: /danke

Der Server verarbeitet die Anmeldung und schickt den Browser per 303 auf die Danke-Seite. Ein Reload lädt dann nur die Bestätigung — nicht die Anmeldung erneut.

3 · Das Grundgerüst: <form>

Ein Formular ist der bequeme Weg, eine HTTP-Anfrage zusammenzuklicken. Zwei Attribute steuern das Ziel:

<form action="/anmeldung" method="post">
    … Felder …
</form>
AttributBedeutung
actionWohin die Daten gehen (URL). Fehlt es, geht die Anfrage an die eigene Seite.
methodWie: get (Standard, in die URL) oder post (im Body).
enctypeKodierung des Bodys (Abschnitt 7). Standard: application/x-www-form-urlencoded.

Ein Formular ohne action schickt an die eigene URL — praktisch zum Ausprobieren, gefährlich beim versehentlichen Reload.

4 · name ist der Schlüssel

Jedes Steuerelement mit einem name geht als Paar name=wert an den Server. Ohne name wird nichts gesendet — das Feld existiert für den Server nicht.

<input type="text" name="name">       <!-- kommt an: name=…   -->
<input type="text" name="email">      <!-- kommt an: email=…  -->
<input type="text">                    <!-- KEIN name → wird NICHT gesendet -->

name ist also der Schlüssel — nicht zu verwechseln mit id (für <label for> und CSS) oder mit dem Beschriftungstext. Ein Feld braucht oft beides: id zum Verknüpfen, name zum Senden.

5 · Die Steuerelemente

ElementWofür
<input>Feld; das type bestimmt die Art: text, email, password, number, date, search, checkbox, radio, file, hidden, submit …
<label for="id">Beschriftung, klickbar mit dem Feld verbunden — hilft Maus und Screenreader.
<textarea>mehrzeiliger Text (Wert steht zwischen den Tags)
<select> + <option>Auswahlliste; gesendet wird der value der gewählten Option
<button type="…">submit (Standard!), reset oder button
<fieldset> + <legend>gruppiert zusammengehörige Felder (z. B. eine Optionsgruppe)
 
<label for="kurs">Kurs</label>
<select id="kurs" name="kurs">
    <option value="html-css">HTML &amp; CSS</option>
    <option value="typescript">TypeScript</option>
</select>

<textarea id="nachricht" name="nachricht" rows="3"></textarea>

Ein Button darf das Formular auch überstimmen: formaction und formmethod am Button überschreiben die Angaben des Formulars — nützlich für „Speichern" und „Löschen" mit derselben Feldsammlung.

6 · GET oder POST?

GETPOST
Wo?im Query-String der URL (?q=…)im Body der Anfrage
Sichtbar?ja — in URL, Verlauf, Lesezeichennein — nicht in der URL
Für was?Lesen: suchen, filtern, teilenVerändern: anlegen, senden, löschen
Wiederholbar?ja (idempotent)nein — zweimal absenden = zweimal anlegen

Merksatz: GET liest, POST verändert. Passwörter oder große Datenmengen gehören nie in eine GET-URL.

7 · enctype — was für ein Body wird das?

  • application/x-www-form-urlencoded — Standard; Paare werden als schlüssel=wert mit & verbunden.
  • multipart/form-data — Pflicht für Datei-Uploads; der Body zerfällt in mehrere Teile (Datei + Textfelder).
  • text/plain — nur zum Debuggen.
<form action="/upload" method="post" enctype="multipart/form-data">
    <input type="file" name="foto">
    <button>Hochladen</button>
</form>

Ohne multipart/form-data schickt ein Datei-Feld nur den Dateinamen, nicht den Inhalt.

8 · Was der Browser wirklich schickt

URL-Encoding: Im Body sind nur bestimmte Zeichen erlaubt. Reservierte Zeichen werden kodiert — Leerzeichen zu + (oder %20), @ zu %40, Umlaute zu %C3%BC usw.

<!-- Eingaben im Formular -->
name = Ada Lovelace
email = ada@example.org
kurs = typescript

<!-- tatsächlicher Request-Body (eine Zeile) -->
name=Ada+Lovelace&email=ada%40example.org&kurs=typescript&agb=on

Der Browser sendet eine Anfrage, lädt dann die Antwort und zeigt sie an. Am Ende bleibt der Server zustandslos: Er merkt sich nichts von der vorigen Anfrage.

StatusBedeutung hier
200 OKAntwort geliefert (z. B. das Formular selbst)
303 See OtherRedirect-after-POST → Browser lädt das Ziel per GET
400 Bad RequestEingaben ungültig — der Server weist die Anfrage ab
404 / 500falsche URL / Fehler im Server

Reload-Falle: Ohne Redirect schickt F5 das Formular erneut — bei einer Bestellung wäre das eine zweite Bestellung. Deshalb endet ein POST auf Erfolg mit 303.

9 · Native Validierung — und ihre Grenze

Der Browser prüft vor dem Senden, wenn Sie ihm Regeln geben:

<input type="email" name="email" required>
<input type="text" name="name" required minlength="2">
<input type="text" name="plz" pattern="[0-9]{4}">
<input type="checkbox" name="agb" required>

<!-- novalidate schaltet die Prüfung des Browsers komplett ab -->
<form action="/anmeldung" method="post" novalidate> … </form>

Nie dem Client vertrauen: Wer die DevTools öffnet oder einen REST-Client nutzt, umgeht jede Browser-Prüfung. Die Prüfung im Browser ist Komfort — die echte Prüfung passiert am Server.

10 · Parallelkonzept: ein Endpunkt, zwei Clients

Dieselbe URL /anmeldung wird auf zwei Weisen angesprochen. Welcher Weg gilt, entscheidet der Content-Type:

ClientContent-TypeAntwort
Browser-Formularapplication/x-www-form-urlencoded303 → /danke
REST-Client / fetchapplication/json201 + JSON

In VS Code sendest du die zweite Variante mit der Extension REST Client aus einer .http-Datei — jede Anfrage mit ### getrennt, per „Send Request" abgeschickt:

### Formular absenden — wie der Browser
POST http://localhost:8000/anmeldung
Content-Type: application/x-www-form-urlencoded

name=Ada+Lovelace&email=ada%40example.org&kurs=typescript&agb=on

### Derselbe Endpunkt als JSON — 201 statt 303
POST http://localhost:8000/anmeldung
Content-Type: application/json

{ "name": "Grace Hopper", "email": "grace@example.org",
  "kurs": "react", "agb": true }

Das lauffähige Beispiel findest du im Begleitprojekt km8-01-hono-formulare (Deno + Hono) — es liefert das Formular, den Endpunkt und die fertige requests.http. Der Weg zum Server ist dort derselbe wie hier beschrieben; das Backend selbst ist POS-Stoff.

12 · Typische Fehler

  • Kein name — das Feld wird nie gesendet. Anti-Beispiel: <input type="email">
  • method="get" für eine Änderung — die Daten landen sichtbar in der URL und im Verlauf: <form action="/anmeldung" method="get">
  • <button> ohne type — der Standard ist submit: <button>Abbrechen</button> schickt das Formular ab. Richtig: <button type="button">.
  • Datei ohne multipart — <input type="file"> ohne enctype="multipart/form-data" überträgt nur den Dateinamen.
  • Nur im Browser validieren — der REST-Client umgeht das. Der Server muss selbst prüfen.

14 · Zusammenfassung & Ausblick

BausteinMerksatz
actionwohin gesendet wird
methodGET liest (URL), POST verändert (Body)
nameder Schlüssel — ohne name wird nichts gesendet
enctypeurlencoded (Standard) · multipart für Dateien
RequestContent-Type + urlencoded Body
Antwort303-Redirect-after-POST · 400 bei ungültig

Ausblick: Dasselbe Senden übernimmt später der fetch-Aufruf in React — statt eines Browser-Redirects liest die App die JSON-Antwort selbst. Genau dort knüpft der REST-Konsum an, den wir in dieser Lektion schon mit dem VS-Code-Client vorweggenommen haben.
