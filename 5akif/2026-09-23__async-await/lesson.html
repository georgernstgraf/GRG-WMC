3 · Inkrementeller Aufbau

Schritt 0 — Recap: Promise-Kette mit .then()/.catch()

Vom 18.9. (Promise-Recap) bekannt: Ein Promise ist ein Versprechen für einen zukünftigen Wert — zunächst pending, dann settled (resolved/rejected). Verkettet wird mit .then(), Fehler landen im .catch():

function pipelineDann(auftrag: Auftrag, karte: string, plz: string): void {
    bestellen(auftrag.artikel, auftrag.menge)
        .then((b) => bezahlen(b, karte))     // jeder .then braucht wieder return
        .then((b) => liefern(b, plz))
        .then((b) => console.log("✅ fertig", b))
        .catch((err) => console.log("🛑", err.name, err.message));
}

Tippfehler-Gefahr vom Recap: vergessenes return in der Kette — dann ist der Wert der nächsten Stufe undefined (genau das steht im promise-demo.ts vom 18.9.).

Schritt 1 — async/await: gleiche Kette, liest sich wie Sequenz

Jede Stufe ist eine async function. Mit await liest sich die Kette wie ein sequentieller Ablauf; Fehler wandern in try/catch:

Runtime ist Deno: deno run demo.ts führt TypeScript direkt aus — kein Transpile-Schritt (Motto vom 11.9.: Jedes JavaScript ist auch gültiges TypeScript). deno check demo.ts prüft die Typen. Im catch-Block ist err vom Typ unknown — der Helfer fehlerText(err) macht die Meldung lesbar. 
async function pipeline(auftrag: Auftrag, karte: string, plz: string): Promise<void> {
    try {
        const b  = await bestellen(auftrag.artikel, auftrag.menge);
        const b2 = await bezahlen(b, karte);
        const b3 = await liefern(b2, plz);
        console.log("✅ fertig", b3);
    } catch (err) {
        console.log("🛑 irgendein Fehler:", fehlerText(err));
    }
}

Das fängt alle Exceptions der Pipeline — sagt aber nicht, aus welcher Stufe der Fehler kommt.

Schritt 2 — Kern der UE: individuelle Exceptions pro Stufe

Daten-Formen: Ein Auftrag (artikel, menge) geht in die Pipeline, wird zur Bestellung (mit Bestellnummer) und reichert sich stufenweise an:

interface Auftrag {
    artikel: string;
    menge: number;
}

interface Bestellung extends Auftrag {
    nr: number;
    zahlung?: string;    // von bezahlen ergänzt
    tracking?: string;   // von liefern ergänzt
}

Die Stufen selbst sind async functions, die über einen Simulations-Helper (simulate(ms, wert) — ein new Promise mit setTimeout) laufzeitähnlich warten; jede wirft im Fehlerfall eine eigene Exception (eigene Error-Klasse, Erben von Error):

const simulate = <T>(ms: number, wert: T): Promise<T> =>
    new Promise((resolve) => setTimeout(() => resolve(wert), ms));

const fehlerText = (err: unknown): string =>
    err instanceof Error ? err.message : String(err);

class ValidationError extends Error {
    constructor(artikel: string, menge: number) {
        super(`Ungültige Bestellung: ${menge}x "${artikel}"`);
        this.name = "ValidationError";   // name setzen, sonst "Error"
    }
}

class PaymentError extends Error {
    constructor(karte: string) {
        super(`Zahlung fehlgeschlagen: Karte ${karte} abgelehnt`);
        this.name = "PaymentError";
    }
}

class ShippingError extends Error {
    constructor(plz: string) {
        super(`Lieferung nicht möglich: PLZ ${plz} außerhalb des Lieferraums`);
        this.name = "ShippingError";
    }
}

Der Konsument der Pipeline kann mit instanceof unterscheiden, wer geworfen hat — Variante A,

try {
    const b  = await bestellen(auftrag.artikel, auftrag.menge);
    const b2 = await bezahlen(b, karte);
    const b3 = await liefern(b2, plz);
    console.log(`✅ Pipeline fertig:`, b3);
} catch (err) {
    if (err instanceof ValidationError) {
        console.log(`🛑 Stufe bestellen: ${err.message}`);
    } else if (err instanceof PaymentError) {
        console.log(`🛑 Stufe bezahlen: ${err.message}`);
    } else if (err instanceof ShippingError) {
        console.log(`🛑 Stufe liefern: ${err.message}`);
    } else {
        console.log(`🛑 Unbekannter Fehler: ${fehlerText(err)}`);
    }
}

… oder granular mit eigenem try/catch pro Stufe — Variante B (Weiterarbeit nach Fehlschlag möglich):

let b: Bestellung;
try {
    b = await bestellen(auftrag.artikel, auftrag.menge);   // wirft ValidationError
} catch (err) {
    console.log(`🛑 Abbruch: ${fehlerText(err)}`);
    return;                                                // ohne Bestellung geht nix
}

try {
    b = await bezahlen(b, karte);                          // wirft PaymentError
} catch (err) {
    console.log(`⚠️ Bezahlung fehlgeschlagen — andere Karte versuchen?`);
    b = await bezahlen(b, "4242-1111-1111-1111");          // Fallback-Karte
}

try {
    await liefern(b, plz);                                 // wirft ShippingError
} catch (err) {
    console.log(`⚠️ Lieferung fehlgeschlagen (${fehlerText(err)})`);
    throw err;                                             // Re-Throw nach Logging
}

Merke: instanceof folgt der Vererbungskette des konkreten Objekts — deshalb fängt err instanceof PaymentError wirklich nur PaymentError-Instanzen (und Subklassen), nicht ValidationError oder ShippingError.

Schritt 3 — finally + Re-Throw

finally läuft immer — egal ob Erfolg, Abfangen oder Re-Throw. Ideal für Aufräumarbeiten:

try {
    // Pipeline
} catch (err) {
    // Typ-Verzweigung (Variante A)
} finally {
    console.log("— Pipeline beendet");
}

Ein Re-Throw (throw err; im catch-Block) loggt lokal und lässt den Fehler nach oben weiterlaufen — siehe Hauptprogramm in demo.ts (Variante B, Stufe liefern):

5 · Typische Fehler (Anti-Beispiele)

Anti-BeispielWas passiert
 
const b = bestellen();
const b2 = bezahlen(b);   // await fehlt!
 Ohne await ist b ein Promise, nicht das Bestell-Objekt. bezahlen(b, …) bekommt kein nutzbares Objekt. Folge: b.menge ist undefined. 
// außerhalb einer async function:
const b = await bestellen();
 await nur innerhalb von async-Funktionen (Ausnahme: Modul-Ebene, top-level await). Sonst SyntaxError. 
catch (err) {
    // „vorübergehend": nur console.log
}
 Fehler verschluckt: Die Pipeline „läuft weiter", obwohl sie gestorben ist. Besser: loggen und throw err oder sinnvoll weiterarbeiten (Variante B). 
try { … } catch (err) { }
try { … } catch (err) { }
 Ein catch ohne Auswertung (kein instanceof, kein name-Check) liest sich leicht, ist aber in einer 3-Stufen-Pipeline allein zu generisch — Variante A/B kombinieren!

6 · Zusammenfassung

Thema.then()/.catch()async/await + try/catch
LesbarkeitKette: hängt pro Stufe ein .then()Sequenz liest sich wie synchroner Code
Fehlerbehandlungein .catch() am Ende der Kettetry/catch um die awaited Aufrufe
Typ-Differenzierungim .catch() mit instanceof prüfeninstanceof im catch oder try pro Stufe
Granularitätein catch = „irgendwo"pro Stufe: Fallback/Weiterarbeit möglich
Warum individuelle Exceptions pro Stufe?

Jede Pipeline-Stufe hat eigenen Domänen-Fehlergrund (Ungültige Bestellung / Kartenausschluss / Lieferraum). Der Aufrufer kann dann mit instanceof gezielt reagieren — oder fährt pro Stufe eine eigene catch-Logik (Variante B). Genau das ist der Kern dieser UE.
