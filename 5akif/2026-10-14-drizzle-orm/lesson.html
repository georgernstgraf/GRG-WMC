1. Die Einstiegsfrage

Du kennst node:sqlite — so haben wir bisher mit SQLite aus TypeScript gesprochen. Drei Zeilen, drei Fehlerquellen:

const rows = db.prepare(
  `SELECT titel, dauer_sek FROM track WHERE album_id = ?`
).all(albumId);

Frage: Wer schreit — und wann —, wenn in dieser Zeile „track“ mit „tracks“ verwechselt wurde, die Spalte „dauer_sek“ falsch getippt ist oder das ? am Ende vergessen ging? Antwort: die Datenbank, zur Laufzeit — möglichst im Demo-Kunde vor Publikum. TypeScript sieht in dem Template-String nur eine Zeichenkette. Genau hier setzt Drizzle an.

2. Das Ziel: dieselbe Frage, aber mit Rückgrat

Nach der Lektion sieht dieselbe Frage so aus — und zwei der drei Fehler von eben wären schon beim Schreiben unmöglich geworden:

const zeilen = await db.select({
    titel: track.titel, dauer: track.dauerSek,
  })
  .from(track)
  .where(eq(track.albumId, albumId));
// erzeugtes SQL (toSQL()):
//   select "titel", "dauer_sek" from "track" where "track"."album_id" = ?
//   params: [ albumId ]

Der Tabellenname kommt aus dem Schema, die Spalte aus dem Schema, das Ergebnis ist ein typisiertes Objekt. Falsch getippte Namen schreien bei der Typ-Prüfung, nicht im Demo-Kunde.

3. Was ein ORM tut — und was nicht

ORM = Object-Relational Mapping: Zeilen aus relationalen Tabellen werden zu Objekten in der Programmiersprache hin und her gemappt. Drizzle ist dabei sehr SQL-nah — der Query-Builder liest sich fast wie SQL, und man kann sich das erzeugte SQL jederzeit ansehen.

Merke Ein ORM ersetzt SQL nicht, es erzeugt es. Wer den Query-Builder versteht, aber das erzeugte SQL nicht lesen kann, versteht nichts — wer SQL kann, liest Drizzle-Queries wie Prosakommentare.

Drei Schmerzen löst Drizzle konkret: Tippfehler wandern zur Typ-Prüfung, Werte sind immer parametrisiert (kein Injection-Handwerk), und Zeilen kommen als typisierte Objekte an statt als lose Spaltenwerte.

4. Schritt 1 — das Schema in TypeScript

Das Herzstück von Drizzle: die Tabellen stehen als TypeScript-Objekte im Code. Wir modellieren unseren Musik-Katalog:

import { sqliteTable, text, integer } from "drizzle-orm/sqlite-core";

export const artist = sqliteTable("artist", {
  id: integer("id").primaryKey({ autoIncrement: true }),
  name: text("name").notNull(),
  gruendungsjahr: integer("gruendungsjahr"),
});

export const album = sqliteTable("album", {
  id: integer("id").primaryKey({ autoIncrement: true }),
  titel: text("titel").notNull(),
  jahr: integer("jahr"),
  artistId: integer("artist_id").notNull().references(() => artist.id),
});

Jede Spalte hat zwei Namen: den TypeScript-Namen (aus dem Code spricht man album.artistId) und den Datenbank-Spaltennamen (artist_id, snake_case wie gewohnt). Der Typ der Spalte (integer, text) bestimmt, welchen TypeScript-Typ das Ergebnis später hat — gruendungsjahr ohne .notNull() ist number | null.

Wichtig sqliteTable(...) erzeugt keine Tabelle in der Datenbank! Es definiert nur, wie Tabellen und Zeilen in TypeScript aussehen. Die Tabellen selbst legt unser db.ts mit DDL an — Migrationen mit drizzle-kit sind Stoff der KM6-Vertiefung.

5. Schritt 2 — die Verbindung

Drizzle braucht einen Treiber, der SQLite spricht. Wir nehmen node:sqlite — derselbe eingebaute Treiber wie bisher, Deno bleibt die Runtime, es kommt kein Node-Zwang dazu:

import { DatabaseSync } from "node:sqlite";
import { drizzle } from "drizzle-orm/node-sqlite";

const client = new DatabaseSync(pfad);
const db = drizzle({ client });
Stolperfalle aus der Praxis drizzle(client) ohne geschweifte Klammern ruft den Pfad-Overload auf — Drizzle baut intern eine eigene Verbindung und findet deine Tabellen nicht („no such table“). Immer drizzle({ client }).

6. Schritt 3 — Lesen: select, where, orderBy

import { eq, desc } from "drizzle-orm";

// alle Alben eines Artists, neueste zuerst:
const alben = await db.select()
  .from(album)
  .where(eq(album.artistId, 1))
  .orderBy(desc(album.jahr))
  .limit(3);

Der Query-Builder liest sich von innen nach außen wie SQL — und genau dieses SQL erzeugt er. Ansehen mit .toSQL():

db.select().from(album).where(eq(album.artistId, 1)).toSQL();
// { sql:    'select "id", "titel", "jahr", "artist_id"
//             from "album" where "album"."artist_id" = ?',
//   params: [ 1 ] }

Zwei Beobachtungen: Drizzle listet die Spalten explizit auf (selbst wo du select() ohne Argumente schreibst), und der Wert 1 steht nicht im SQL-Text, sondern im params-Array — Parametrisierung by default.

Das Ergebnis sind typisierte Objekte: alben[0].titel ist ein string, alben[0].artistId der TypeScript-Name — die Spalte heißt in der DB trotzdem artist_id.

7. Schritt 4 — Schreiben: insert, update, delete

// einfügen — und die neue Zeile inkl. vergebener id zurückbekommen:
const neu = await db.insert(album)
  .values({ titel: "Silent Lines", jahr: 2015, artistId: 1 })
  .returning();
// [ { id: 1, titel: "Silent Lines", jahr: 2015, artistId: 1 } ]

// ändern — gezielt, mit where:
await db.update(track)
  .set({ dauerSek: 220 })
  .where(and(eq(track.albumId, 1), like(track.titel, "Silent%")));

// löschen — ebenso gezielt:
await db.delete(track).where(eq(track.titel, "Echo Room"));

Die Regeln aus SQL bleiben dieselben: Ein update oder delete ohne where trifft alle Zeilen — Drizzle hindert dich nicht daran, nur ersetzt es die Zeichenketten durchschaubaren Code. Und die Fremdschlüssel aus dem Schema lebt die Datenbank: Ein Album mit artistId 99, ohne Artist 99, stirbt mit FOREIGN KEY constraint failed — die DB schützt die Konsistenz, nicht das ORM.

8. Schritt 5 — Auswerten: join, count, groupBy

import { count } from "drizzle-orm";

// Wie viele Tracks hat jedes Album?
const auswertung = await db.select({
    titel: album.titel, tracks: count(),
  })
  .from(track)
  .innerJoin(album, eq(track.albumId, album.id))
  .groupBy(album.id);

// [ { titel: "Silent Lines", tracks: 2 } ]

Der innerJoin nimmt die Verbindungsbedingung explizit (eq(track.albumId, album.id)) — du siehst dieselbe JOIN-Logik wie in SQL, nur getippt statt geschrieben. Aggregationen (count, auch sum/avg) kombinieren mit groupBy genau wie im SQL-Kern von KM5.

9. Unter die Haube: erzeugtes SQL lesen

.toSQL() ist euer Röntgenblick — ohne Ausführung, nur Text:

import { gt } from "drizzle-orm";

const q = db.select().from(track)
  .where(and(eq(track.albumId, 1), gt(track.dauerSek, 180)))
  .limit(3);

console.log(q.toSQL().sql);
console.log(q.toSQL().params);
// select "id", "titel", "dauer_sek", "album_id"
//   from "track"
//   where (("track"."album_id" = ?) and ("track"."dauer_sek" > ?))
//   limit ?
// params: [ 1, 180, 3 ]

Drei Werte, drei Parameter, kein einziger Wert im SQL-Text. Das ist dieselbe Parametrisierung, die ihr aus db.prepare(...).run(?) kennt — Drizzle macht sie zur Norm, statt sie zur Disziplin zu erklären.

10. Wann trotzdem Raw SQL?

Drizzle ist Werkzeug, nicht Dogma. Weiter Raw SQL (node:sqlite direkt) ist die richtige Wahl, wenn:

  • die Auswertung SQL-spezifische Mächtigkeit braucht: Unterabfragen/CTEs aus KM5-03 — Drizzle kann vieles, aber SQL bleibt mächtiger;
  • du messen willst: EXPLAIN QUERY PLAN ist SQL-CLI-Territorium, kein Query-Builder;
  • es um Betrieb geht: .import, VACUUM INTO, Backup-Skripte — Werkzeugkette statt Programmcode.
Merke Die SQL-Kompetenz aus KM5-02 bis KM5-04 ist der Kern — Drizzle ist der Typsicherheits-Layer obendrauf. Wer das erzeugte SQL nicht lesen kann, baut blind.

11. Typische Fehler

  • await vergessen: Der Query-Builder ist lazy — ohne await passiert schlicht nichts (das Query-Objekt liegt herum).
  • drizzle(client) statt drizzle({ client }): Drizzle baut eine eigene Verbindung und meldet „no such table“ — Falle war real, beim Bau dieses Projekts.
  • Erwartung, sqliteTable lege Tabellen an: Das Schema ist Definition, keine DDL — die Tabellen-Anlage läuft über DDL/Migrationen.
  • Namen vertauscht: album.artistId im Code, artist_id in der DB — wer den DB-Namen im Code sucht, sucht vergebens, und wer den TS-Namen im SQL-Text sucht, auch.
  • update/delete ohne where: trifft alle Zeilen — im Code wie in SQL eine der teuersten Flüchtigkeitsfehler überhaupt.
  • Werte per String-Interpolation in Raw-SQL: `... WHERE titel = '${x}'` ist Injection-Futter — im Query-Builder parametrisiert Drizzle, bei Raw-SQL parametrisierst du.
